Event Record

Every call to a Sartre event generator returns an Event object. It holds the event kinematics, its coherent or incoherent classification, and a list of Particle records connected by parent and daughter indices. This page explains how to use that information in an analysis program. The class references remain the authoritative API documentation.

Obtaining and retaining an event

The exclusive Sartre and inclusive SartreInclusiveDiffraction generators both return a pointer to their current event:

Event* event = sartre.generateEvent();
event->list();

The generator owns this object and replaces it when the next event is generated. Read or store the information needed for an event before calling generateEvent() again. If an application needs an in-memory event collection, make a copy:

std::vector<Event> savedEvents;

Event* event = sartre.generateEvent();
savedEvents.push_back(*event);

For large samples, writing only the variables and particles needed for analysis is generally more practical than retaining all events in memory. The supplied examples show one ROOT-based layout; it is a convention of the example programs, not a file format imposed by the library.

Event-level kinematics and traits

The scalar fields in Event describe the generated interaction. Momentum-like quantities use GeV and squared quantities use GeV2.

Field
Use in an analysis
eventNumberSequential generated-event number.
Q2, W, x, y, sDIS kinematics: photon virtuality, photon--hadron centre-of-mass energy, Bjorken x, inelasticity, and squared beam centre-of-mass energy.
t, xpomMomentum transfer and diffractive momentum fraction.
polarizationSelected photon polarization: transverse or longitudinal.
diffractiveModecoherent when the target remains intact and incoherent when it dissociates or is excited.
crossSectionRatioLTRecorded longitudinal-to-transverse cross-section ratio for the selected point.
beta, z, MX, quarkSpeciesInclusive-diffraction variables: diffractive Bjorken variable, longitudinal momentum variable, diffractive mass, and selected quark-species index. They are meaningful for SartreInclusiveDiffraction.

In exclusive ep and eA production, the familiar fields through xpom are the principal event observables. In inclusive diffraction, also retain beta, z, MX, and the Pythia-generated hadrons described below. UPC uses quasi-real transverse photons and has its own conventions; see Ultra-Peripheral Collisions.

Particle records and relationships

Event::particles is a std::vector<Particle>. A particle's index equals its position in that vector. Its parents and daughters contain indices into the same vector, which lets an analysis follow a particle history without pointers.

Particle field
Meaning
pdgIdPDG particle identifier. Nuclear ions and fragments use nuclear PDG identifiers.
statusGenerator status. In normal Sartre output, 1 denotes a final particle, 2 a decayed or intermediate particle, and 4 an incoming beam particle.
pTLorentzVector four-momentum, with components available through Px(), Py(), Pz(), and E().
parents, daughtersZero, one, or more vector indices defining the record's particle graph.

The electron beam travels in negative z and the hadron beam in positive z. For nuclei, the four-momentum recorded by Sartre is expressed per nucleon. The detailed Particle reference includes the status-code and nuclear-PDG conventions.

Current record layouts

For the ep and eA workflows, the initial beam entries are stable: index 0 is the incoming electron and index 1 is the incoming proton or nucleus. UPC uses a special hadron--hadron beam convention described on the UPC page. The supplied main programs use the following layouts after a successful event generation. Treat the remaining index positions as a useful current convention, not as an application-level guarantee; inspect event->list() after updating Sartre or changing final-state options.

Exclusive diffraction

Index
Record entry
0Incoming electron.
1Incoming proton or nuclear target.
2Scattered electron.
3Virtual photon.
4Produced vector meson or DVCS final state.
5Diffractive exchange (pomeron documentation entry).
6Scattered target. For an incoherent nuclear event it can be an intermediate parent of breakup products.

If the example program is configured to decay the vector meson, it appends the decay daughters and marks the parent at index 4 as decayed. If nuclear breakup is enabled for an incoherent nuclear event, stable breakup fragments are appended after the main exclusive record.

Inclusive diffraction

Index
Record entry
0Incoming electron.
1Incoming proton or nuclear target.
2Scattered electron.
3Virtual photon.
4Scattered target.
5, 6Partonic quark and antiquark produced by the diffractive system.
7 onwardPythia 8 shower and hadronization record. A particle with status == 1 is a final-state Pythia particle suitable for final-state analyses.

For a q–q̅–g contribution, an intermediate gluon is also present before the Pythia record. Nuclear-breakup products, when enabled, are appended after the Pythia entries. The numberOfPythiaParticlesStored field is used by the distributed inclusive example while transferring Pythia particles into ROOT. Because this field and the detailed Pythia layout are implementation details, retain the full particles vector or use the example's logic when an analysis depends on Pythia ancestry.

Writing ROOT output

Sartre itself returns C++ objects; it does not automatically write an event file. The main programs demonstrate one convenient ROOT representation:

  • sartreMain.cpp writes an event branch of exclusive scalar kinematics and separate TLorentzVector branches for the incoming and outgoing beams, virtual photon, and vector meson.
  • sartreInclusiveDiffractionMain.cpp adds beta, z, and MX, records the partonic quark and antiquark, and stores stable Pythia particles in a TClonesArray branch named pythia.

The inclusive example's essential selection is:

pythia.Clear();
for (int i = 7; i < event->numberOfPythiaParticlesStored; ++i) {
    const Particle& particle = event->particles[i];
    if (particle.status == 1)
        new (pythia[pythia.GetEntries()]) TLorentzVector(particle.p);
}
tree.Fill();

Adapt branches, particle selection, and metadata to the intended analysis, but save the runcard, random seed, and table identity with the ROOT file. The Example Program Walk-Through describes both example programs in detail.

Checks and important caveats

  • Call event->list() for the first few events of every new configuration. It prints scalar kinematics followed by index, PDG ID, name, status, parent/daughter indices, and four-momentum for each particle.
  • Do not retain the generator-owned Event* past the next call to generateEvent(); copy it or write out the information first.
  • Do not assume that a particle is final merely because it has a familiar PDG ID. Select final states using status == 1 and the parent/daughter graph where appropriate.
  • For nuclear momenta, remember the per-nucleon convention before forming energies or comparing them with whole-ion quantities.
  • With nuclear breakup enabled, the legacy Gemini++ breakup treatment supplies baryonic fragments but not photons. The resulting event record is therefore not strictly energy--momentum complete. Document this when using breakup fragments in an analysis.

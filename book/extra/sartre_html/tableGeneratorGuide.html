Table Generator Guide

Expert reference for producing, combining, and validating Sartre amplitude and cross-section tables. Table production encodes physics and numerical choices; it is not an ordinary event-generation step. Prefer a released, compatible table set whenever one is available.

What a table-generation run calculates

Sartre event generation is fast because it interpolates quantities calculated in advance. The expensive integrations over impact parameter and, where applicable, fluctuating target configurations are performed when the tables are made. Consequently, a table set is valid only for the physics configuration and phase space used to create it.

Exclusive diffractionTables over Q2, W, and t, containing amplitude moments used for coherent and incoherent vector-meson or DVCS cross sections.
Inclusive diffractionFour-dimensional tables over β, Q2, W, and z. The current calculation stores the transverse q̅q, longitudinal q̅q, and transverse q̅qg contributions for the supported quark flavours.
UPCTwo-dimensional transverse-amplitude tables over xpom and t, produced by the dedicated UPC generator for the ultra-peripheral-collision calculation path.

The table format, lookup hierarchy, and inspection tools are described in Tables and Table Tools. Runcard keywords are documented in the Runcard Reference.

Before starting a production

  • Start from a runcard that produced a validated, nearby table set; preserve a copy with the output.
  • Fix the target, dipole model, particle or process, fluctuation settings, kinematic range, binning, and integration mode before splitting work over a cluster.
  • Make a small trial range first, inspect it, and establish the required disk space and run time. Do not use a sparse trial as a production table.
  • Record the Sartre revision, build options, ROOT version, runcard, and command ranges. These are needed to reproduce or safely merge the result.
  • Place the finished, complete set in the normal tables/<A>/<model>/<process>/ hierarchy only after it has passed validation.

Generator programs and bin ranges

When the corresponding build option is enabled, Sartre installs the following table-production executables. The three main generators divide their work by an inclusive global-bin range:

# Exclusive diffraction
tableGeneratorMain tableGeneratorRuncard.txt startBin endBin

# Inclusive diffraction
tableGeneratorInclusiveDiffractionMain tableGeneratorInclusiveDiffractionRuncard.txt startBin endBin

# Ultra-peripheral collisions
tableGeneratorUPCMain tableGeneratorUPCRuncard.txt startBin endBin

# Legacy proton lambda-correction tables
lambdaGeneratorMain tableGeneratorRuncard.txt startBin endBin

For tableGeneratorMain, tableGeneratorInclusiveDiffractionMain, and tableGeneratorUPCMain, startBin and endBin are both included. Adjacent jobs must therefore use non-overlapping ranges, for example 0 999 and 1000 1999. They are global table-bin indices, not values of a physics variable. lambdaGeneratorMain is different: its ending bin is excluded; see Lambda-correction generator.

Exclusive, conventional integrationThe full range has Q2bins * W2bins * tbins bins.
Exclusive, FFT modeThe outer work range has Q2bins * W2bins rows; each row produces all t values supplied by the transform.
Inclusive diffractionThe full range has betabins * Q2bins * W2bins * zbins bins.
UPCThe full range has xbins * tbins bins, with axes in xpom and t.
Lambda correctionThe full range has Q2bins * W2bins * tbins bins. This legacy program uses an end-exclusive job interval.

UPC table generator

tableGeneratorUPCMain creates the amplitude tables used by Sartre's ultra-peripheral-collision (UPC) calculation. Start from tableGeneratorUPCRuncard.txt, which enables UPC=true and specifies the target, vector meson, dipole-model parameters, amplitude-moment mode, configuration count, substructure setting, and the xmin, xmax, tmin, tmax, xbins, and tbins grid. The supplied runcard is an example, not a production prescription.

The generator makes transverse tables for the first amplitude moment, its squared moment, and its variance. When A=1, modesToCalculate is not 1, and numberOfConfigurations=1, it also makes real-part and skewness correction tables. The output file name is marked with _UPC. Use the same model, target, meson, and fluctuation settings when running the UPC event calculation; a UPC table is not interchangeable with an ordinary exclusive table.

The source's banner still contains an old usage label that names tableGeneratorMain. Invoke the installed executable named tableGeneratorUPCMain, as shown above. It accepts an inclusive range, so a split such as 0 999 followed by 1000 1999 covers each requested global bin once. The useBackupFile and startingBinFromBackup controls are available, but should be tested on a small run before a long production.

Lambda-correction generator

lambdaGeneratorMain is a legacy, developer-oriented program for making proton real-part correction tables. It derives a transverse and a longitudinal lambda_real table on the ordinary exclusive Q2, W2, t grid. For each bin it estimates the energy derivative of the logarithm of the amplitude by finite differences in W2. It is not a general table generator and does not create inclusive or UPC tables.

Although it reads an exclusive table-generator runcard, the program explicitly forces A=1, modesToCalculate=1, and numberOfConfigurations=1. It must therefore not be used to produce nuclear, fluctuating-target, or multi-configuration correction tables. Treat it as an expert compatibility utility and begin with the same validated exclusive runcard and binning as the amplitude table it is intended to accompany.

Unlike the main generators, its loop is startBin <= bin < endBin: endBin is excluded. Adjacent jobs should consequently be written as 0 1000 and 1000 2000. Its partial output names include the starting bin and the polarization suffix, for example _bin0_T.root and _bin0_L.root. Inspect and merge these partial tables only after confirming that their metadata and grids match.

Runcard and production controls

Exclusive production is configured by tableGeneratorRuncard.txt; inclusive production uses tableGeneratorInclusiveDiffractionRuncard.txt; and UPC production uses tableGeneratorUPCRuncard.txt. The runcard specifies the same physical model inputs that event generation must later match. In particular, changing the target mass, dipole model, meson, substructure, number of configurations, or kinematic limits requires compatible tables. The lambda utility reads the exclusive runcard but overrides several of its target and configuration controls, as described above.

For exclusive tables, modesToCalculate selects which amplitude moments are made. In conventional mode, options distinguish an analytical first moment, a configuration-averaged first moment, and the second moment. This choice controls which coherent and incoherent observables can be evaluated. Use the comments in the supplied runcard and the validated table set as the authority for a production choice.

Important numerical controls include Q2bins, W2bins, tbins, numberOfConfigurations, and the integration tolerances. Inclusive tables additionally require the β and z ranges and their bin counts. fractionOfBinsToFill is useful for a quick test only; a released table must cover its declared grid. Exclusive jobs can write periodic backup files when useBackupFile is enabled, but backup and recovery behaviour should be verified in a small test before relying on it for a long campaign.

DFT/FFT calculation path

For the exclusive calculation, the current source offers a two-dimensional discrete Fourier-transform path controlled by useFFT and nFFT. It computes the impact-parameter transform on a grid and supplies all transformed t values for each outer (Q2, W2) row. This is particularly relevant to nuclear calculations, where direct multidimensional integration of second moments can be very costly.

The 2026 EIC@BNL talk reports a roughly 2,000-fold speed-up for the shown second-moment calculation, with the demonstrated calculation changing from about a week to minutes. The same talk quotes 2,000–7,000 for optimised examples. These are method- and setup-dependent benchmarks, not guaranteed production timings. They are nevertheless the reason new nuclear table campaigns should evaluate the FFT path first.

In FFT mode the traditional tbins, tmin, and tmax controls are not the normal way of choosing the transform output. nFFT must be even. Custom arbitrary t grids are an expert, source-level path in the current generator and should be reviewed carefully before use. The nThreads setting controls OpenMP parallel work only when Sartre was built with OpenMP support; confirm this in the build before planning resource use.

Merging and validation

Produce disjoint partial ranges with otherwise identical settings, then combine only compatible results. Use tableMerger -n as a dry run before writing a merged table. Missing bins and zero-valued bins must be understood rather than silently accepted.

Use tableInspector on every output and final merged table to check table metadata, dimensions, phase-space coverage, and content statistics. tableQuery can probe interpolation at representative points. Compare overlaps between independently produced pieces, inspect edge bins, and make a small event-generation test with the intended runcard. The tableInspector reference lists the available checks.

Machine-learning work and numerical quality

Older numerical table workflows could exhibit isolated spikes from difficult integrations and interpolated dipole-model lookup functions. Sartre-related research has investigated neural-network fitting as a way to identify or smooth such numerical artefacts. The newer DFT/FFT approach discussed in the 2026 talk is designed to avoid the numerical-glitch workflow for the demonstrated exclusive transform calculation.

Machine learning is not presently exposed as a general, turnkey command-line option in the Sartre table generators. It remains an expert analysis and validation method: preserve the unmodified numerical tables, validate any fit against independent points and physical constraints, and never substitute a fitted table for a production result without documented checks. The operational ML workflow for Sartre 2 remains TBD.
